# Design: UI, prototypes, figures, and visual systems

Use for HTML artifacts, interfaces, dashboards, visual prototypes, figure concepts, and design direction.

## Start from context

Inspect supplied brand rules, tokens, code, screenshots, assets, copy, and constraints before inventing a design. If a known visual reference matters, extract general principles or authorized tokens; do not clone proprietary screens or distinctive branded flows. When context is absent, define a small system: palette, type hierarchy, spacing, surfaces, radii, and interaction posture.

Design around the user's primary decision or action. Use real content or clearly marked placeholders; never invent metrics, testimonials, or product claims. For dashboards, every datum should support an action.

## Explore with purpose

When direction is uncertain, produce two or three variants that differ in a meaningful stance (for example density, hierarchy, layout, or interaction model), not merely color. For a one-off mockup, use self-contained HTML with realistic content and a visible state change. For a repository feature, use the actual stack and existing components instead.

Avoid default visual sludge: gradients, glass effects, generic card grids, random icon sets, fake charts, and oversized rounded boxes are not hierarchy. Use type, whitespace, alignment, contrast, and a restrained accent first. Maintain keyboard/focus affordances, adequate hit targets, responsive behavior, and reduced-motion support where relevant.

## Figure and prototype QA

Make data-to-claim relationships immediately legible. Check hierarchy, reading order, labels, units, contrast, spacing, image provenance, and visual clutter. Open the artifact at the intended viewport, check console errors, test the main interaction and important states, and inspect a screenshot before delivery.
